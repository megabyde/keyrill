# Разработка

Версия Rust закреплена в файле `rust-toolchain.toml` на значении 1.99.1; используются редакция 2024
и resolver 3. Файл `Cargo.lock` хранится в репозитории, и каждая проверка запускается с флагом
`--locked`, так что зависимости никогда не обновляются незаметно. Ядро использует только стандартную
библиотеку; крейт `keyrill-ffi` в macOS дополнительно подключает `libc` ради констант открытия
файлов. Библиотеки proptest и serde_json нужны только тестам. Добавлять асинхронную среду
выполнения, библиотеку пользовательского интерфейса или второй движок не следует.

В macOS, кроме того, необходимы Command Line Tools и clang-format 23.1.3 (устанавливается командой
`pip install clang-format==23.1.3` в виртуальном окружении). Xcode не требуется.

> [!NOTE]
> Проверки следует запускать от имени обычного пользователя: один из тестов рассчитывает на отказ в
> доступе к файлу, а пользователь root такого отказа не получает.

```console
$ ./tools/verify
```

Команда `make check` выполняет то же самое; каждый из перечисленных ниже режимов также доступен как
цель make (например, `make sanitize`). Команда `make help` выводит остальные цели: `format`,
`bundle`, `status` и `install`.

Проверка по умолчанию запускает `pack-model.py --check` и `check-excerpts.py` (последний сверяет
фрагменты кода из учебника с исходными текстами), rustfmt, Clippy с предупреждениями в качестве
ошибок, все тесты, включая doctest, rustdoc с предупреждениями в качестве ошибок, release-сборку и
синтаксическую проверку заголовочного файла как кода на языке C, а также компонует и запускает
дымовой тест C ABI. В macOS она, кроме того, проверяет форматирование нативного кода и файлы plist,
запускает статический анализатор Clang, рассматривая его замечания как ошибки, собирает приложение и
инструменты и выполняет контролируемые нативные тесты.

| Режим | Что требуется | Что выполняется |
| -- | -- | -- |
| `sanitize` | macOS | Нативные тесты под ASan/UBSan; библиотека на Rust не инструментируется |
| `browser-fixture` | Node 18+ | Детерминированные проверки браузерного стенда на JavaScript |
| `markdown` | uv | mdformat и pymarkdown закреплённых версий по всей документации и сверка русских переводов с исходными страницами; `markdown fix` переформатирует файлы |
| `site` | mdbook 0.5.4, mdbook-mermaid 0.17.1 | Сборка сайта, публикуемого `pages.yml`, в каталог `target/site/book`; при битой ссылке сборка прекращается |
| `audit` | cargo-deny 0.20.2 | Проверка уязвимостей, источников, лицензий и запретов для графов зависимостей приложения и фаззинга |
| `coverage` | cargo-llvm-cov 0.6.21, `llvm-tools-preview` | Покрытие кода на Rust по строкам и областям, нижняя граница 95 % |
| `evaluate` | Python 3 | Оценка модели без обращения к сети (см. раздел [«Движок»](engine.ru.md#%D0%BE%D1%86%D0%B5%D0%BD%D0%BA%D0%B0)) |
| `fuzz` | cargo-fuzz 0.13.2, nightly-2026-10-26 | 10 000 случаев для текста, разборщиков и состояния и 200 случаев для файла модели, начальное значение 126283 |
| `miri` | Miri и rust-src для nightly-2026-10-26 | Тесты указателей и протокола FFI |

Фаззинг выводит путь к временному каталогу с журналами, пополненными корпусами и артефактами сбоев;
сбой воспроизводится запуском той же цели с путём к артефакту. Входными данными для фаззинга модели
служат ограниченные правки настоящего файла модели. Под Miri пропускаются тесты чтения файлов и
полный обход неизменяемой модели, который под Miri занял бы около 26 минут; эти тесты выполняются в
обычном наборе. Покрытие измеряется только для кода на Rust; нативный код в него не входит.

Тесты режима совместимости создают настоящие события Quartz и потому требуют сеанса WindowServer. В
изолированной командной оболочке функция `CGEventSourceCreate` может вернуть null, хотя вне изоляции
те же тесты проходят; о таком случае следует сообщать как о сбое окружения, а не подменять
кодировщик событий.

## Стиль

Используются стандартные правила rustfmt и проверки Clippy, а также `missing_docs`,
`clippy::missing_errors_doc` и `clippy::missing_panics_doc`; ограниченный `#[allow]` допускается
только там, где рядом записана причина. В ядре `unsafe` запрещён; в крейте `keyrill-ffi` запрещено
`unsafe_op_in_unsafe_fn`, и для каждого небезопасного блока указаны его предусловия. Нативный код
оформляется по `.clang-format` (стиль LLVM, отступ 2 пробела); код на Rust использует принятый в
rustfmt отступ 4 пробела. Ширину отступа редакторам сообщает файл `.editorconfig`. Комментарий
должен объяснять, зачем написан код, а не пересказывать, что он делает.

Публичные элементы на Rust оформляются в соответствии с
[API Guidelines](https://rust-lang.github.io/api-guidelines/documentation.html): строка краткого
описания, раздел `# Errors` (а также `# Panics` или `# Safety`, где они применимы) и исполняемый
пример у точек входа. Примеры являются doctest, поэтому `cargo test` компилирует и выполняет их;
вместо `unwrap` в них используется `?` со скрытыми строками `# fn main() -> Result<...>`. Типы
ошибок реализуют `std::error::Error` и выдают сообщения, не содержащие пользовательских данных.
Внутридокументные ссылки на элементы, существующие только в macOS, нарушают сборку документации в
Windows, поэтому такие элементы следует называть просто моноширинным шрифтом. См. также
[Rust Style Guide](https://doc.rust-lang.org/stable/style-guide/) и раздел о FFI в
[Rustonomicon](https://doc.rust-lang.org/nomicon/ffi.html).

Тест должен ограничивать поведение, а не просто выполнять код: для нативных сценариев — проверки
всего документа, для вывода — точные причины и замены, тесты свойств — с фиксированным начальным
значением; в тестах состояния не допускаются паузы и время по системным часам. См. раздел
[«Тестирование»](testing.ru.md).

## Изменения

Сообщения коммитов оформляются по правилам
[Conventional Commits](https://www.conventionalcommits.org/), с указанием области там, где это
полезно (`feat(macos):`, `fix(core):`). В индекс добавляются точные пути, а документация обновляется
в том же изменении, что и поведение. Изменения нативного кода и ABI требуют, кроме того, запуска
`./tools/verify sanitize` и просмотра фактического диффа вместе с его отрицательными сценариями.
Изменение политики или модели требует повторной оценки.

Рядом с каждой страницей, перечисленной на сайте, лежит её русский перевод с суффиксом `.ru.md`
(`docs/engine.ru.md` переводит `docs/engine.md`); переводы собственных страниц сайта находятся в
`site/ru/`. Русскую страницу следует изменять в том же коммите, что и её английский источник, и
переносить новое значение `git hash-object` источника в первую строку русской страницы; до тех пор,
пока они не совпадут, `./tools/verify markdown` завершается с ошибкой.

Система непрерывной интеграции (`.github/workflows/verify.yml`) запускает проверку по умолчанию на
`macos-15`, `windows-2025` и `ubuntu-24.04`, санитайзеры в macOS, проверку Markdown в Linux и
отдельные задания аудита, покрытия, Miri, фаззинга и оценки. Действия (Actions) закреплены по хешу
коммита, токен выдаётся только для чтения, а checkout не сохраняет учётные данные. Ни одно задание
ничего не подписывает, не публикует и не устанавливает. Задание покрытия прикладывает одностраничный
HTML-отчёт (`target/llvm-cov/keyrill-coverage.html`), который открывается в браузере со страницы
запуска, и помещает таблицу по файлам в сводку запуска. Dependabot ежемесячно предлагает обновления
Cargo и Actions; версия инструментов Rust, дата nightly, версии инструментов, устанавливаемых через
`cargo install`, и зависимости Python для генератора модели закрепляются вручную — последние потому,
что их обновление требует пересоздания модели.
